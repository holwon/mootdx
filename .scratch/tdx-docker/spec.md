# mootdx 常驻服务：TCP 桥协议 + Docker 镜像分发

Status: ready-for-agent

> **来源**：本 spec 由 `/to-spec` 于 2026-10-17 从一轮 `/grill-with-docs` 的裁决合成（13 条决策 + 端口策略 + 5 条实现默认）。上游消费者是 `holwon/astock-mcp` 的通达信源（见其 `docs/adr/0019`）；本次变更推翻该 ADR 的决定 1 / 3 / 5，关闭理由见 `## Further Notes`。

## Problem Statement

mootdx 目前向外部宿主提供数据的唯一形态是 `mootdx worker`：一个**一次性 stdio 子进程**，宿主负责拉起它、喂 stdin、读 stdout、崩溃后重建、退出时收掉进程树。

这对使用方（`astock-mcp`）意味着三件事：

1. **用通达信源就必须先装 Python**。用户得自建 venv、安装 fork、把 `Scripts\python.exe` 的绝对路径填进 MCP 客户端配置。路径填错、装成非 editable 版本、Store 别名存根……每一种都表现为「配置了但没生效」，排查成本极高（本仓已实际踩过两次）。
2. **进程生命周期成了宿主的重担**。截至本次变更，`astock-mcp` 为此写了 775 行进程管理（握手、判坏、退避重建、杀整棵进程树、stderr 转发），另有约 600 行测试与两份假 worker 夹具——全部是在替 Docker 该做的事。
3. **本仓库的 `Dockerfile` 形同虚设**：它的入口是 `mootdx --help`，即一次性 CLI，不是常驻服务；也没有任何镜像发布流水线。

对本仓库自身也有代价：`mootdx worker` 的唯一消费者就是那个 stdio 宿主，一旦换形态，这 200 行就是一个没有消费者的代码路径。

## Solution

把 `worker` 子命令改造成 **`serve` 子命令**：一个常驻的 **TCP** 服务，复用**完全相同**的行式 JSON 帧协议（v1），只把承载从 `stdin/stdout` 换成 socket。

- 使用方只需 `docker run` 一个**已发布到 ghcr.io 的镜像**，然后配置 `host:port`。不装 Python、不管进程、不配路径。
- 镜像官方发布：`ghcr.io/holwon/mootdx`，tag 推送时出 `v*` + `latest`，同时构建 `amd64` 与 `arm64`。
- `mootdx worker`（stdio）**删除**——它没有剩余的消费者。
- 缓存目录 `~/.mootdx`（复权数据 `xdxr`、服务器测速结果）在镜像里声明为卷，容器重建不丢。

**一句话**：同一个协议，换一个承载，包一层镜像。

## User Stories

### 作为使用者：获取与启动

1. 作为使用者，我想用一条 `docker run` 就把通达信数据服务跑起来，以便不接触 Python 环境。
2. 作为使用者，我想镜像同时支持 `amd64` 与 `arm64`，以便 Apple Silicon 与 x86 服务器都能直接拉。
3. 作为使用者，我想从 `ghcr.io/holwon/mootdx` 直接拉镜像而不需要登录或额外凭据，以便一条命令可用。
4. 作为使用者，我想 tag 推送时自动发布新镜像（`vX.Y.Z` 与 `latest`），以便不需要手工构建与上传。
5. 作为使用者，我想 PR 上也能构建镜像但不推送，以便 Dockerfile 腐化在合并前就被发现。
6. 作为使用者，我想容器默认监听一个固定端口（7701），以便配置端点是可预测的。
7. 作为使用者，我想能改监听端口，以便 7701 被占用时仍可使用。
8. 作为使用者，我想在端口已被占用时看到**清晰的启动错误**（而非静默失败或假装的空监听），以便自己就知道该改什么。
9. 作为使用者，我想文档给出**只绑回环**的端口映射示例（`-p 127.0.0.1:7701:7701`），以便我不会不小心把服务暴露给整个局域网。
10. 作为使用者，我想文档解释**为什么**示例里带 `127.0.0.1:` 前缀，以便我明知风险时能自行去掉。
11. 作为使用者，我想文档给出 `--restart unless-stopped` 的示例，以便机器重启或进程崩溃后服务自己回来。
12. 作为维护者，我想 README / 文档首页有「一行命令启动」的入口，以便新人不读全文档也能跑起来。

### 作为使用方（astock-mcp 这类宿主）

13. 作为宿主开发者，我想连接一个 `host:port` 就能取数，以便不需要知道对端是 Docker、裸机进程还是另一台机器上的服务。
14. 作为宿主开发者，我想连接建立后服务端**主动**先发 `hello` 再发 `ready`，以便我能区分「TCP 通了」与「真的能取数」（后者要探测通达信服务器，约 3.4 秒）。
15. 作为宿主开发者，我想 `hello` 帧带协议版本与 mootdx / python 版本，以便版本不匹配时我能显式失败而不是静默降质。
16. 作为宿主开发者，我想协议帧形状与 v0.x 完全一致（`id` / `method` / `params` → `id` / `ok` / `bars` 或 `error`），以便已有的解析代码一行不改。
17. 作为宿主开发者，我想连接关闭就等价于「会话结束」（服务端释放该会话的资源），以便我不需要额外的 shutdown 消息。
18. 作为宿主开发者，我想服务端在 `ready:false` 之后**保持监听**，以便网络恢复后我重连就能成功，而不是发现容器已经退出。
19. 作为宿主开发者，我想多个客户端能同时连接（各自独立的握手与请求队列），以便多个 MCP 会话共享同一个数据服务。
20. 作为宿主开发者，我想一个客户端的慢速/挂起请求不影响另一个客户端，以便一个坏掉的使用者不会拖垮其他使用者。
21. 作为宿主开发者，我想服务端能承受客户端「连了不发请求」的情形而不泄漏资源，以便长跑的服务不会因为一次探测连接而变慢。
22. 作为宿主开发者，我想文档写明「服务端不主动断开空闲连接」，以便我知道什么时候该自己实现超时。

### 作为使用者：缓存与网络

23. 作为使用者，我想复权数据（`xdxr`）缓存在容器卷里，以便第二次请求快（热路径约 46ms，冷路径约 3.8s）。
24. 作为使用者，我想容器在**不挂卷**时也能工作，以便我只想临时跑一下时不必管理卷。
25. 作为使用者，我想文档给出**命名卷**的示例，以便我能在多个容器之间复用同一份缓存。
26. 作为使用者，我想容器仍能通过出站 TCP 7709 连通达信服务器，以便它真的能取到数据（镜像不改变数据来源）。
27. 作为使用者，我想文档明确写出「容器需要出站 7709，不需要任何入站放行（除了映射端口）」，以便企业网络下我知道找网管开什么。
28. 作为使用者，我想连不上通达信服务器时看到 `ready:false` 与具体错误文本，以便区分「我的网络问题」与「对端服务问题」。
29. 作为使用者，我想容器日志走 `docker logs` 直接可读（stdout 不再被协议占用），以便排障不需要额外工具。

### 作为使用者：从旧形态迁移

30. 作为使用者，我想文档有一节「从 `mootdx worker` 迁移」，以便我从 stdio 形态切过来时知道该删什么、该改什么。
31. 作为使用者，我想删除 stdio 形态时**没有兼容层**（不保留 `worker` 子命令），以便代码里不留一条没有消费者的死路径。
32. 作为使用者，我想命令行 `--help` 里不再出现 `worker`，以便不会被一个已废弃的入口误导。

### 作为维护者：代码与测试

33. 作为维护者，我想协议的实现（`serve(reader, writer, factory)`）在改造中**一行不改**，以便既有的 11 个协议用例原样通过。
34. 作为维护者，我想新增的传输层是一条薄封装（监听、接受、为每个连接跑一遍 `serve`），以便协议逻辑与传输逻辑的边界清晰。
35. 作为维护者，我想「多会话互不干扰」有确定性测试，以便并发行为被钉住。
36. 作为维护者，我想「端口被占用」有确定性测试，以便启动失败的表现被钉住。
37. 作为维护者，我想既有的真网络用例（`network` 标记）从「spawn 子进程」改为「连 TCP」，以便真网络路径仍有一等公民覆盖。
38. 作为维护者，我想 CI 只跑非网络用例并额外 `docker build`，以便流水线不依赖外网通达信服务器。
39. 作为维护者，我想 Dockerfile 是多阶段构建（builder 里出 wheel、final 层只装 wheel），以便镜像不带构建工具。
40. 作为维护者，我想镜像以非 root 用户运行（若 base 镜像允许），以便不是一个安全反模式。
41. 作为维护者，我想镜像带一个轻量健康检查，以便 `docker ps` 能看出「容器活着但连不上通达信服务器」与「容器健康」的区别。
42. 作为维护者，我想 `pyproject.toml` **不新增任何运行时依赖**（TCP 用标准库 `socketserver` / `socket`），以便发布物不增重。

### 作为使用者：可观测性

43. 作为使用者，我想服务端日志里能看到「监听在哪个地址端口」，以便确认配置生效。
44. 作为使用者，我想日志里能看到「每个连接来自哪里、何时断开」，以便排查连接泄漏。
45. 作为使用者，我想日志里能看到所选通达信服务器 IP 与探测耗时，以便判断网络质量。
46. 作为使用者，我想调试级别的日志能看到每个请求的方法名与耗时，以便定位慢请求。

## Implementation Decisions

### 传输层（本批的核心改动）

- **`serve` 子命令取代 `worker`**。命令名 `serve`，参数 `--host`（默认 `0.0.0.0`）与 `--port`（默认 `7701`）。删除 `worker` 子命令及其入口，`--help` 中不再出现。
- **帧协议 v1 完全不变**。`hello` / `ready` / `req` / `resp` / `err` 五种消息的形状、字段名、`id` 回执语义一字不改；**协议版本号仍为 1**（升版本会让既有客户端无谓地判坏）。帧格式的唯一权威是 `docs/cli/serve.md`（原 `docs/cli/worker.md` 改名）。
- **协议核心不改**：`serve(reader, writer, factory)` 的签名与实现保留。传输层只负责「把 socket 的两端包装成 reader/writer，然后调它」。这是本批最重要的结构约束——它让既有的 11 个协议用例零改动。
- **每连接一个会话，且每连接一个独立的行情客户端**。这是**强制**而非优化：底层 `tdxpy` 客户端持有一个 socket，同一实例上的并发请求会交错、破坏协议流。因此每个连接自己 `factory()` 一个新客户端，连接关闭时 `close()` 它。
- **服务器探测结果进程内共享**。探测一台可用通达信服务器实测约 3.4 秒；若每个连接各自探测，多客户端场景会成倍变慢。故首次探测的结果缓存在进程级，后续连接复用（但仍各自持有独立的协议 socket）。
- **`ready:false` 不终止进程**。握手失败（连不上任何通达信服务器）时服务端如实回 `ready:false` + 错误文本，然后**继续监听**等待下一个连接；该连接上后续请求回 `ok:false`（错误文本说明 not ready）。这样网络恢复后重连即可，不需要重启容器。
- **异常隔离**：单连接内的畸形请求、客户端中途断开、客户端不发请求就断开，都只影响该连接；不得让监听循环退出。
- **不主动断开空闲连接**。宿主侧的超时是宿主的责任；服务端不猜。
- **并发模型**：每连接一个线程（标准库 `socketserver.ThreadingTCPServer` 或等价）。协议本身是单飞行（一次一条请求-应答），所以每连接内部不需要额外锁。

### 依赖

- **零新增运行时依赖**。监听与并发用标准库。日志沿用既有 `mootdx.logger`（stderr）。
- stdout 因协议搬走而空出——保留给未来可能的诊断输出，本批不使用。

### 镜像

- **多阶段构建**：builder 阶段出 wheel，final 阶段只装 wheel（不带编译工具链与源码树）。
- **入口 = `serve`**，默认参数在镜像里给定（`--host 0.0.0.0 --port 7701`）。容器内**必须**监听 `0.0.0.0`，否则 Docker 端口映射不可达——这是机制要求，不是可选项。
- **`VOLUME /root/.mootdx`**：容器重建（不删容器）时缓存保留；`docker run --rm` 或删容器则丢失。文档给出命名卷复用示例。
- **`EXPOSE 7701`** 仅作文档性声明。
- **健康检查**：用一条**不发网络请求**的本地探活（例如对监听端口做一次 TCP 连接并读 `hello` 帧），使「容器活着」与「能取数」可区分。**不得**用「能否连上通达信服务器」做健康检查——那会让上游抖动导致容器被判不健康而重启。
- **非 root 运行**：若 base 镜像与卷权限允许则启用；若与 `VOLUME` 权限冲突，允许退回 root 并在 Dockerfile 注释说明原因。
- 关闭 `PYTHONDONTWRITEBYTECODE` 之外的行为保持不变；`PYTHONUNBUFFERED=1` 保留（日志实时可见）。

### 镜像发布流水线

- 触发：push tag `v*` → 构建并推送 `ghcr.io/<owner>/mootdx:<version>` 与 `:latest`。PR / push master → 只构建、不推送。
- 平台：`linux/amd64` + `linux/arm64`（buildx）。
- 认证：用 `GITHUB_TOKEN`（`packages: write`），不引入额外密钥。
- 现有 `django.yml`（pytest + wheel）保持不变，新增的镜像工作流与之并列。

### 文档

- `docs/cli/worker.md` → **`docs/cli/serve.md`**，内容重写为 TCP 形态（帧格式章节保留、迁移自 stdio 的说明、`docker run` 示例、端口与卷说明、故障排查表）。`mkdocs.yml` 同步改标题与路径。
- `docs/chlog.md` 记一条：`worker` → `serve`，stdio → TCP。
- README 增加「用 Docker 跑」的入口段。

## Testing Decisions

**什么是好测试**：只测外部行为——帧的往返、连接的生命周期、并发隔离、启动失败的表现；不测私有方法、不断言实现细节、不断言线程数。

**Seam 1（协议层，已有、最高、零改动）**
- 现有的 `serve(reader, writer, factory)` 与 `tests/test_worker.py` 的 11 个用例**原样保留**：握手形状、`ready:false` 后的错误应答、字段裁剪、错误回收、EOF 退出。这条缝用内存流（`StringIO` / `BytesIO`）+ 假行情客户端驱动，确定、快速、不需要网络。
- 新增用例：**两个独立会话并发驱动同一个 `serve` 的两次调用**，断言两者互不干扰（一方的请求不会出现在另一方的输出流里）。这条用例直接由 seam 1 覆盖，不需要开 socket。

**Seam 2（传输层，新增、唯一新缝）**
- 被测对象是「监听 + 接受 + 每连接跑 serve」的那层封装。
- 测试用 `127.0.0.1` 与**系统分配端口**（`port=0`，从监听对象读回实际端口），因此不依赖固定端口、可并行。
- 用例：
  1. 连上后按序收到 `hello` 与 `ready`；发一条 `daily_kline` 收回应答且 `id` 对应。
  2. 两个客户端同时连上，各自独立完成握手与请求，互不看到对方的帧。
  3. 一个客户端连上后保持沉默，另一个客户端的请求照常被服务（隔离）。
  4. 客户端连接后立即关闭，服务端不崩、仍可接受下一个连接。
  5. **端口已被占用**时启动抛明确异常（先用一个占位 socket 占住端口）。
  6. 客户端发畸形行（非 JSON）时，该连接收到 `ok:false`（或按既有语义断开），服务端仍存活。
- 先例：本仓 `tests/test_worker.py` 的假客户端风格；`test_bestip.py` 中的本机 socket 用法。

**真网络（`network` 标记，默认套件排除）**
- `tests/test_worker_live.py` 从「spawn 子进程并喂管道」改为「起一次 TCP 服务（或连一个已在跑的实例）并走 socket」。断言内容不变：hello→ready→60 根日 K→字段与单位→UTF-8 往返→未知方法存活。
- 运行方式写进文件头 docstring（沿用现行惯例）。

**镜像（不做自动化，仅 CI 构建 + 手测）**
- PR 上 `docker build` 成功即为通过（验证 Dockerfile 不腐化）。
- 端到端（`docker run` → 连上 → 取数）属人工验收，记录在对应票的 Comments。

**回归面**
- 既有非网络用例必须全绿且**零改动**（除 `test_worker.py` 文件若改名需同步，本 spec 建议**不改名**以保住零改动）。
- `pyproject.toml` 依赖列表不得新增条目。

## Out of Scope

- **HTTP / REST / WebSocket 承载**。已否决：为一台机器上的进程间调用引入一整套 HTTP 栈不值；调试便利不足以抵消依赖重量。
- **保留 stdio 路径**。`worker` 子命令删除，不留兼容层、不留 `--stdio` 开关。
- **服务端鉴权 / TLS**。当前场景是本机回环或内网可信环境，且数据是公开行情；不引入凭据体系。
- **服务端管理进程（Docker socket / 容器编排）**。本服务只做数据服务，不负责拉起或重启自己。
- **宿主侧重试与退避**。那是使用方的责任（`astock-mcp` 将删除自建的退避逻辑，改由 Docker `--restart` 承担）。
- **其他数据面**（quote / ticks / 分钟 K / 财务 / 除权）。本批只搬承载，`daily_kline` 仍是唯一方法；`method` 命名空间继续为后续预留。
- **多版本协议适配**。单版本握手，不匹配即 `ready:false` / 判坏。
- **Windows / macOS 原生运行承诺**。服务本身是纯 Python 无平台专有代码，但官方分发形态是容器；非容器用法（`pip install` 后手工 `mootdx serve`）不作为承诺面。
- **镜像体积优化到极致**。多阶段 + 精简基座即可，不做 distroless 迁移。

> **2026-10-18 修订（实测否证了本条的原前提）**：原文写「不做 Alpine 迁移（`pandas` 在
> musl 上代价高）」，实测该前提不成立——`pandas` / `numpy` / `wcwidth` 在 musl 上**都有
> musllinux wheel**，全程不编译，装出来 146 MB（glibc 侧 142 MB，仅多 4 MB）；而基座从
> `python:3.12-slim`（177 MB）换成 `python:3.12-alpine`（83 MB）**省 94 MB**。
> 净效果：镜像 445 MB → 368 MB。已在 `linux/amd64` 与 `linux/arm64`（QEMU）双架构实测：
> 握手、60 根日 K、单位与复权口径全部正常，冷 10.05s / 热 0.06s（amd64），
> 冷 10.41s / 热 0.17s（arm64）。

## Further Notes

### 为什么推翻了上游 ADR-0019

`astock-mcp` 的 ADR-0019 曾明确否决「本地 sidecar」形态，理由是「为一台机器上的进程间调用引入端口 / 防火墙 / 生命周期三重额外面」。本次反转的根据是**那三条理由在容器形态下都不再成立**：

| 原否决理由 | 容器形态下 |
|---|---|
| 端口成为额外负担 | 端口成为**特性**——它就是配置面，比路径更稳、可跨机器 |
| 防火墙 | Docker 管端口映射；用户侧只需 `-p`，无新增面 |
| 生命周期 | 交给 `docker run -d` + `--restart`，比自建退避重建简单可靠 |

同时，原形态的真实代价在实施后暴露：宿主要为「进程管理」写 775 行 + 约 600 行测试，而这些全是 Docker 的职责。这是**代价测量错误**，不是新需求。

原 ADR 中**不受影响**的部分：worker 代码住在本 fork 内、首批只做日 K、挂降级链尾、单位在 C# 适配器归一、协议纪律（stdout 只走协议、UTF-8、`id` 回执）。

### 破坏性变更，但当前无版本负担

本仓最后一个 tag 是 `v0.1.3`，早于 `worker` 子命令的引入；`worker` / `serve` 这条线**从未发布过**。因此删除 stdio 路径不构成对任何已发布版本的破坏，也不需要迁移兼容层。

### 一处已知的语义收紧

旧 stdio 形态下，宿主关闭 stdin 即等价于「会话结束」。TCP 形态下这个信号不复存在——改为**连接关闭即会话结束**。对使用方而言语义等价（都是「我不再需要这个会话」），但实现上从「读流 EOF」变成「读 socket 返回空」。

### 协议核心不动是本次设计的关键

把「帧的形状」与「帧的承载」分开，使得：

- 已发布的协议文档几乎不用改（只改承载说明与调用方式）
- 既有的 11 个协议用例一行不改
- 未来若真需要 HTTP 或 Unix socket 承载，只是再加一层薄封装

这条约束应作为代码评审的硬标准：**任何触碰 `serve(reader, writer, factory)` 内部实现的改动，都要说明为什么承载层做不到**。
